# 一、基础篇：线程怎么用

## 题 1 · 并发初体验：串行 vs 并发

🎯 **目标**：亲眼看到"并发 ≠ 更快，而是**不用干等**"。

📝 **要求**

1. 写 `work(name, seconds)`：打印 `[start] 名字`，`time.sleep(seconds)`，打印 `[end] 名字`
2. **串行**调用 3 次（各 1 秒），用 `time.perf_counter()` 计时并打印总耗时
3. **并发**：3 个线程各跑 1 秒，同样计时打印

🔍 **预期现象**

- 串行：约 **3 秒**
- 并发：约 **1 秒**

💡 **提示**：`threading.Thread(target=work, args=("A", 1))`，然后 `start()` / `join()`。

❓ **自测（能答出来才算懂）**

1. `sleep` 的时候 CPU 在忙吗？那为什么并发能省时间？
2. 如果把 `work` 里的 `sleep` 换成纯计算（比如累加一千万次），并发还会是 1 秒吗？
3. 这题说明了什么任务适合多线程？（关键词：**I/O 密集**）

## 题 3 · `join`：让主线程等一等

🎯 **目标**：理解 `join` 阻塞的是**调用它的那个线程**。

## 题 4 · `daemon`：主线程退出了，子线程怎么办

🎯 **目标**：搞清"主线程结束"和"进程结束"是两件事。

📝 **要求**

写一个长任务线程：循环 10 次，每次打印心跳并 `sleep(0.5)`（共约 5 秒）。
主线程 `sleep(1)` 后打印 `[主线程] 结束`。

- **版本 A**：不设 daemon（默认 False）
- **版本 B**：`t.daemon = True`

🔍 **预期现象**

- A：主线程 1 秒后打印结束，但**程序还要再等约 4 秒**才退出（子线程跑完 10 次）
- B：主线程结束后**程序立刻退出**，心跳只打了两三次就没了

💡 **提示**：`t.daemon = True` 必须在 `t.start()` **之前**设置。

❓ **自测**

1. daemon 设晚了（start 之后）会怎样？
2. 为什么 daemon 线程适合"后台心跳/日志"，不适合"必须写完文件"的任务？

# 二、同步篇：共享数据怎么不打架

## 题 5 · 竞态条件与锁（⭐ 本章最重要的一题）

🎯 **目标**：亲手撞出"丢失更新"，理解为什么**有 GIL 也照样要加锁**。

📝 **要求（四小步，每步都要看结果）**

**(a) 普通累加 —— 先看看"不撞车"的样子**

8 个线程，每个线程把全局变量 `counter += 1` 共 20 万次。总期望 160 万。

**(b) 同样的题，把 +1 拆成"读-改-写"**

```python
tmp = counter
time.sleep(0)      # 主动让出，制造切换点
counter = tmp + 1
```

8 个线程 × 500 次，期望 4000。

**(c) 给 (b) 加锁**

用 `threading.Lock`，把"读-改-写"三步包进临界区。

**(d) 换个写法**

用 `with lock:` 代替手动 `acquire()/release()`，再跑一遍，结果应该和 (c) 一致。

🔍 **预期现象（实测数据）**

| 小步 | 期望 | 实际 |
|---|---|---|
| (a) 普通 `+=` | 1,600,000 | **1,600,000 —— 完全正确！** |
| (b) 读-改-写 + sleep(0) | 4,000 | **约 700~800（丢了一大半）** |
| (c) 加锁 | 4,000 | 4,000 ✅ |
| (d) `with lock:` | 4,000 | 4,000 ✅ |

💡 **提示**：(a) 跑出来是对的，**不要以为就安全了**——这只是"撞巧了"。CPython 3.14 的 `+=` 执行得极快，两次切换之间很难正好卡在"已读未写"的窗口里。

❓ **自测（这题答得出来才算真懂）**

1. (a) 没出错、(b) 出错，差别到底在哪一步？
2. **"GIL 保证了线程安全"这句话错在哪？**（GIL 只保证"同一时刻只有一个线程执行字节码"，但"读-改-写"是三个步骤，切换可以发生在中间）
3. 为什么加了 `sleep(0)` 就必错？（它主动放弃了 GIL，把切换点塞进了临界区）
4. 加锁之后为什么变慢了？值得吗？

## 题 6 · `RLock`：同一个线程能重复拿同一把锁吗

🎯 **目标**：理解可重入锁，避免"自己把自己锁死"。

📝 **要求**

写一个类，`add()` 方法里先获取锁，然后**再调用同一个类里也需要获取这把锁的** `_write()` 方法（模拟嵌套调用）。

- **版本 A**：用 `threading.Lock()`
- **版本 B**：用 `threading.RLock()`

⚠️ **版本 A 会卡死**，所以**必须用带超时的写法**观察，别真等：

```python
ok = lock.acquire(timeout=1)   # 1 秒拿不到就返回 False
print("第二次获取成功吗?", ok)
```

🔍 **预期现象**

- A（Lock）：第二次 `acquire(timeout=1)` 返回 **False**
- B（RLock）：正常通过，程序正常结束

💡 **提示**：RLock 内部有计数器，同一个线程每 `acquire` 一次 +1，必须 `release` 同样次数才真正释放。

❓ **自测**

1. 什么场景才真的需要 RLock？（嵌套调用 + 同一个锁）
2. 为什么普通 Lock 不可重入？
3. `acquire()` 不带 timeout 时卡死，除了 Ctrl+C 还有别的办法排查吗？

## 题 7 · `Condition`：生产者消费者（基础版）

🎯 **目标**：掌握 `wait()` / `notify()` 的经典用法。

📝 **要求**

用 `threading.Condition` + 一个 `list`（当作容量 3 的缓冲区）实现：

- **生产者**：生产 10 个产品（编号 1~10），缓冲区**满了就等**
- **消费者**：消费 10 个，缓冲区**空了就等**
- 两者都是 `while` 判断 + `wait()`，生产/消费后用 `notify()`

🔍 **预期现象**：程序正常结束（不死锁、不崩），最终"生产 10 个 = 消费 10 个"。

💡 **提示**

```python
with cond:
    while len(buffer) >= 3:      # 必须 while，不能用 if
        cond.wait()
    buffer.append(item)
    cond.notify()
```

❓ **自测**

1. 为什么判断条件要用 `while` 而不是 `if`？（关键词：**虚假唤醒**）
2. `notify()` 和 `notify_all()` 区别？
3. 调 `wait()` 时会自动释放锁吗？（会！否则别人永远进不来）

# 三、进程篇：绕开 GIL

## 题 9 · GIL 实测：线程 vs 进程（⭐ 核心认知题）

🎯 **目标**：用数据证明"Python 多线程跑不满多核，多进程可以"。

📝 **要求**

写一个 CPU 密集函数：

```python
def cpu_work(n):
    s = 0
    for i in range(n):
        s += i * i
    return s
```

用 `n = 20_000_000`，**跑 4 份**，分别测三种方式的总耗时：

1. **串行**：连续调用 4 次
2. **4 线程**：4 个 `threading.Thread`
3. **4 进程**：4 个 `multiprocessing.Process`

用 `time.perf_counter()` 计时，打印加速比（串行耗时 ÷ 并发耗时）。

🔍 **预期现象（实测）**

| 方式 | 耗时 | 加速比 |
|---|---|---|
| 串行 4 份 | 5.09s | 1.00x |
| 4 线程 | 5.06s | **1.01x（等于没加速）** |
| 4 进程 | 1.61s | **3.16x（接近 4 核）** |

💡 **提示**：进程版**必须**放在 `if __name__ == "__main__":` 里；`multiprocessing.cpu_count()` 可以打印核数（你的机器是 **32 核**）。

❓ **自测**

1. 为什么 4 个线程加起来没比串行快？（GIL：同一时刻只有一个线程在跑 Python 字节码）
2. 为什么进程能快？（每个进程有独立的 Python 解释器和 GIL）
3. 那多线程还有什么用？（**I/O 密集**：等网络/磁盘时 GIL 会释放，其他线程能干活）
4. 什么时候用线程、什么时候用进程？各举一个真实场景。

## 题 11 · 进程间通信：为什么进程不能用普通变量

🎯 **目标**：亲身体会"进程的内存是不共享的"。

📝 **要求**

**(a) 用 `multiprocessing.Queue`**
主进程创建 `q`，两个子进程：一个写 3 个值，一个循环读并打印。
收尾：写进程 `join()`，读进程是死循环，只能 `terminate()`。

**(b) 反例实验（很重要）**
把 `Queue` 换成**普通全局 list**：主进程里放 3 个元素，子进程打印这个 list。
观察子进程打印出来的内容。

🔍 **预期现象**

- (a) 能正常读到 3 个值（打印顺序可能交错），程序能正常退出
- (b) 子进程打出来的是 **空列表**（或者主进程的修改看不到）—— **证明进程内存不共享**

💡 **提示**：线程之间共享全局变量，**进程之间不共享**，必须靠 `Queue` / `Pipe` 这类通道。

❓ **自测**

1. 为什么进程之间不能共享普通全局变量？（每个进程有独立地址空间）
2. `Queue` 和 `Pipe` 有什么区别？各适合什么场景？
3. 为什么这里要用 `terminate()` 而不是 `join()`？（读进程是死循环，join 会永远等下去）
